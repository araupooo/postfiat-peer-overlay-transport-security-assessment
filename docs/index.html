Post-Quantum Peer-Overlay Transport Security Assessment

Transport-security assessment of the postfiatd peer overlay under a post-quantum threat model. Pinned tree: postfiatd main commit 0085a1ff885d6a446369cf73a4430f75af22be55. Harness harness.py version 1.0.0, seed 20261113.

Headline findings

  • Peer TLS is TLS 1.2 / 1.3 with a 2048-bit RSA self-signed certificate, and no certificate verification. The overlay context is built by make_SSLContext(""); verification is verify_none on both ends of a peer connection. Peer authentication does not come from TLS at all: it comes from the overlay handshake above TLS, where each peer signs a value derived from the TLS Finished messages with its long-term secp256k1 node key.
  • The cipher list as written is TLSv1.2:!CBC:!DSS:!PSK:!eNULL:!aNULL. Under the local OpenSSL it expands to 31 TLS 1.2 suites. It excludes every CBC suite, but it still permits RSA key transport: 8 RSA suites remain (`AES256-GCM-SHA384`, `AES256-CCM8`, `AES256-CCM`, `ARIA256-GCM-SHA384`, `AES128-GCM-SHA256`, `AES128-CCM8`, `AES128-CCM`, `ARIA128-GCM-SHA256`), and harness variant V5 negotiates TLS_RSA_WITH_AES_256_GCM_SHA384 against the overlay configuration. RSA key transport has no forward secrecy.
  • TLS 1.3 is allowed and is what negotiates by default. Variant V1 (overlay configuration as written) negotiates TLS 1.3 with TLS_AES_256_GCM_SHA384. The cipher list does not touch TLS 1.3 suites at all: the code never calls SSL_CTX_set_ciphersuites, so all default TLS 1.3 suites are available (`TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`, `TLS_AES_128_GCM_SHA256`).
  • Harvest-now-decrypt-later exposure is concentrated in TLS 1.2 sessions. TLS 1.3 sessions use ephemeral (EC)DHE only and are forward-secret against a later quantum adversary. TLS 1.2 sessions negotiated with an RSA key-transport suite are decryptable by anyone who later obtains the (ephemeral, per-process-start) RSA private key together with the recorded session. Ledger data itself is public; session keys and the peer handshake are what a recorded session protects.
  • Hybrid ML-KEM migration is blocked on the pinned OpenSSL, not on the protocol. OpenSSL 1.1.1w has no ML-KEM support; native ML-KEM arrived in OpenSSL 3.5 (8 April 2025). The first migration step is therefore the OpenSSL upgrade, then enabling the X25519MLKEM768 hybrid group (RFC 10024). The overlay's above-TLS peer authentication (secp256k1 node keys) is a separate, harder migration and is out of scope for the transport change.

Full rationale, per class, is in exposure_analysis.md.

What the cipher list does not fix. The overlay's forward secrecy depends on which TLS version and suite the two peers actually negotiate, not on the cipher string alone. Under TLS 1.2 the string still admits RSA key transport; under TLS 1.3 the string is inert. The honest statement is: forward secrecy is guaranteed only for TLS 1.3 sessions and for TLS 1.2 sessions that happen to negotiate (EC)DHE.
Limits — read before citing. The harness measures a local TLS rig configured like the overlay; it is not a measurement of live peer connections — no live peer, validator or network endpoint was contacted. The ledger was not compiled or run. Results depend on the local OpenSSL (library OpenSSL 3.0.13 30 Jan 2024); the pinned library is 1.1.1w. Negotiated cipher suites at runtime depend on the peer's offered list, which is not observable statically. See assumptions.md and claim_evidence_index.md for the full list.
